# Finishing the business day with closing duties still incomplete shows a warn-and-confirm dialog listing them

When a manager hits Finish Day, any closing daily duties still pending close the day anyway — silently. The audit trail is still *correct* per ADR 0001 (the day ended; logs are gone for those duties), but the *meaning* drifts: yesterday's history shows an incomplete close with no marker that anyone noticed. A manager browsing the history viewer (ADR 0004) sees an under-counted closing section and no signal that the under-count was deliberate.

This ADR adds a warn prompt before `finishDay()` runs. It touches no model — `BusinessDay`, `TaskItem`, and `CompletionLog` already carry enough to derive "which closing duties are not yet done in this business day." The new surface is a manager-only `.alert` listing the incomplete duties, driven by a pure helper that computes the list from existing derived state.

## Decisions

- **Policy: Warn (not Block, not Allow-silent).** A non-empty list of incomplete closing duties triggers a `.alert` with two buttons: "Finish Anyway" (calls the existing `finishDay()`) and "Cancel" (does nothing). Warn is the middle path — it forces a deliberate second tap without trapping a manager who legitimately needs to close (e.g. a closing duty was renamed and re-added, the staff member who owns it went home sick). Mirrors the `.alert` UX already established by ADR 0005 (stale-day recovery).
- **Scope: Uniform.** The policy applies to every closing daily duty across every Area — no per-duty criticality, no per-Area variation. A "criticality" flag on `TaskItem` is the natural shape if/when this needs to vary, but introducing one without a real restaurant's input would be guessing. Uniform is the honest starting point.
- **Surfaced in the alert: the duty titles.** The `.alert` message lists each incomplete closing duty under a header line ("N closing duties not marked done:"). A bullet list (`• title`) is the most legible format for a wet-hands manager scanning a phone. Count pluralization handled ("1 closing duty" / "N closing duties").
- **Definition of "closing duty":** `checklist.cadence == .daily && checklist.phase == .closing`. Weekly checklists have `phase == nil` by design (see `Models/Checklist.swift` and CONTEXT.md — weekly duties are bound to a `Weekday`, not a `Phase`), so they are structurally excluded. Opening daily duties are excluded by definition. Orphaned duties (`checklist == nil`) are excluded — they don't belong to any checklist, so they can't be "closing" by definition; ADR 0004's history viewer surfaces them separately as "Other."
- **Completion derived, not stored.** A duty is "done in this business day" iff a `CompletionLog` exists with `businessDay === current` (ADR 0001). No new persisted flag, no new field on `BusinessDay`, no aggregate. The same derivation the duty list uses to render a checkmark.
- **The staleness recovery path (ADR 0005) routes through the same gate.** A manager who taps "Finish Day" on the stale-day alert also gets the warn prompt if closing duties are incomplete. Two reasons: (1) consistency — every finish-day code path receives the same friction; (2) the staleness recovery is *more* likely to be on an incomplete day, not less (the whole reason it went stale is probably that nobody closed it properly).
- **Pure helper, framework-free.** `FinishDayPolicy.incompleteClosingDuties(in:businessDay:) -> [TaskItem]` lives in `checklist-app/Scheduling/`, mirrors the `BusinessDayHealth` / `LogRetention` / `StaffManagement` caseless-enum pattern. Returns `[TaskItem]` rather than `[String]` so the UI can render however it likes (today: bullet list; tomorrow: a sheet with checkboxes). Input order preserved for predictable UI rendering.
- **No audit trail for the override (deferred).** Today, an override is silent — no record that the manager finished with N duties incomplete. A `BusinessDay.closedWithIncompleteDuties: [String]?` snapshot or a `FinishDayOverrideLog` aggregate would be the shape if this surfaces as a need. The history viewer already shows the under-count indirectly (the closing section for that day is sparse); adding a "manager chose to override" signal is a separate audit-trail decision (cf. ADR 0004's deferred `LogMutationAudit`).

## What changes in the existing code

- **New file `checklist-app/Scheduling/FinishDayPolicy.swift`** — caseless enum namespace. One static method: `incompleteClosingDuties(in: [TaskItem], businessDay: BusinessDay) -> [TaskItem]`. Filters by `checklist.cadence == .daily && checklist.phase == .closing && !duty.isDone(in: businessDay)`. Framework-free.
- **New file `checklist-appTests/FinishDayPolicyTests.swift`** — `@MainActor` (matches `AuthStoreTests`); uses an in-memory SwiftData container because the inputs are `@Model` instances with `@Relationship` access. 8 tests pinning: empty input, all-complete happy path, all-incomplete, mixed complete/incomplete, opening duties excluded, weekly duties excluded, orphaned duties excluded, input-order preservation.
- **`checklist-app/ContentView.swift` (`AreaListView`)** — gains `@Query private var allDuties: [TaskItem]` (mirrors `DutyListView`), `@State private var showingFinishDayWarning = false`, `@State private var pendingIncompleteClosingDuties: [TaskItem] = []`. New private method `requestFinishDay()` — computes the list via the helper; empty → calls `finishDay()` directly; non-empty → stashes the list and sets the alert flag. The Finish Day toolbar button's action changes from `finishDay` to `requestFinishDay`. The stale-day alert's "Finish Day" button *also* routes through `requestFinishDay()` (per the decision above). A second `.alert("Finish Day?", isPresented: $showingFinishDayWarning)` is attached to the `NavigationStack`; its message is a multi-line `Text` built from a computed property that pluralizes the header and bullet-lists the titles. The two alerts cannot fire simultaneously (one is `.onAppear` cold-launch, one is button-tap).

## Threat model (unchanged from ADR 0002 / 0003 / 0004 / 0005)

Nothing structural changes. The warn check is read-only; the override is the existing manager-only `finishDay()`. No new privileged surface, no new persistent state, no new authentication boundary. The risk of *not* having this surface (silent meaning-drift in the audit trail; an under-counted close looking like a complete close in history) is greater than the risk of an occasional modal interruption.

## Rejected alternatives

- **Block (force completion first).** Too rigid for real service. A manager who needs to close on a duty that was renamed mid-shift, or whose owner went home sick, is trapped. The data model already accepts an incomplete close (the day ends; the duty just has no log) — blocking would invent a constraint the model doesn't have. Warn preserves manager agency.
- **Allow-silent (current behavior).** The history viewer (ADR 0004) makes this materially worse than when the ticket was first written: yesterday's under-counted close is now browsable and looks indistinguishable from a properly-closed day. Silent allowance defeats the audit-trail value ADR 0001 was built for.
- **Per-duty criticality (e.g. "count drawer" required, "wipe menus" skippable).** Needs real-restaurant input we don't have. A `TaskItem.isCritical: Bool` flag (or a `Criticality` enum) is the shape; uniform application is the honest default until that input arrives.
- **Per-Area policy (FOH stricter than BOH or vice versa).** Same problem — guessing without input. And the natural variation is by *duty*, not by Area (a BOH "count the drawer" is just as critical as an FOH one).
- **`.confirmationDialog` instead of `.alert`.** Action sheets are heavier and feel more "destructive action" than " heads-up." ADR 0005's stale-day alert already established `.alert` as the right tool for finish-day-adjacent warnings; consistency wins.
- **Override audit trail (record "manager finished with N incomplete duties").** Worth doing if it surfaces as a need, but adds schema today for a question nobody has asked. The history viewer's under-count is the indirect signal already. See "Open questions deferred" below.
- **Auto-skip if all incomplete duties are "new today."** Tempting (a duty added at 11:45pm and finished at 11:46pm shouldn't trap the manager), but "new today" is itself a derivation with edge cases (renamed? re-added? same title different ID?). Uniform warn handles the rare case with one extra tap; special-casing it would encode a rule nobody asked for.
- **Persist "don't warn again for this session."** Defeats the feature. The whole point is that every finish-day-with-incomplete-duties is a deliberate choice; persisted dismissal lets the meaning-drift back in silently.
- **Surface the warn from `DutyListView` instead of `AreaListView`.** Wrong scope — finish-day is a single action per business day, not per checklist. `AreaListView` owns the Finish Day button; it owns the gate.

## Open questions deferred to follow-ups

- **Override audit trail** — `BusinessDay.closedWithIncompleteDuties: [String]?` (snapshot of titles at close time, so it survives later duty rename/delete) or a `FinishDayOverrideLog` aggregate (closer to ADR 0004's deferred `LogMutationAudit`). The right shape depends on whether anyone wants to *query* overrides ("how often does this manager close incomplete?") vs. just *see* them in history.
- **Per-duty criticality** — a `Criticality` enum on `TaskItem` (`.required` / `.skippable`), surfaced as a manager-set flag in the (still-unbuilt) duty edit UI (ADR 0003 deferred follow-up). Unblocks a future "only warn on critical" mode without restructuring the helper.
- **Block mode as opt-in** — if real restaurants report that warn is too loose, a `.blockUntilComplete` policy is a one-method addition to `FinishDayPolicy` (the helper already returns the list; the UI swaps an alert for a refusal). Defer until asked.
- **Staff visibility** — staff currently see nothing (Finish Day is manager-only per ADR 0003). If a "you can't leave yet, closing duties are incomplete" staff surface is wanted, it's a separate feature with its own ADR.
